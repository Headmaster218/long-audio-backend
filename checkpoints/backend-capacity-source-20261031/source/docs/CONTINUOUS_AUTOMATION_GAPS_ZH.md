# 持续录音：人工交接之后仍缺什么

当前已验证的固定 FTPS 命名空间、多代目录、逻辑分析结束、结果导出和下一会话创建，是可恢复的**显式单次交接**，不是无人值守连续运行。原始文件的完整性、服务恢复能力和识别质量是三个不同目标。

## 下一步需要补齐的实际行为

1. **持续调度与恢复入口。** 现有 generation transition 完成后只创建并绑定下一会话，不自动启动其 intake。还需要持久记录当前 span，重启后先读取原有收据再继续同一个 runner，不能凭进程退出码另建一条会话。
2. **提前选择边界。** 必须在输入数、帧数或空间额度耗尽前选择完整已发布的 successor，处理尚未完成的上传和已选择未提交的输入。现有容量预检会安全暂停，但不会选择下一批。不能把提高上限当成解决方法。
3. **接收器安全换代。** 现有活动代际在启动时选定，需停机重启；没有上传排空和热切换协议。上传中断可能留下 Android 无法补传的半成品 attempt。所有旧路径和凭据必须继续可用，旧 QUEUED 项仍可能需要新建 attempt，不能仅提供只读旧服务。
4. **不确定会话创建。** POST 已发出但没有确认时，客户端收据故意阻止再次创建。无人值守需要服务器端明确的幂等创建与查询协议；猜测“没成功”并重发会生成重复会话。
5. **推理失败的有限恢复策略。** 中断后的 failed/manual chunk 当前需显式确认同一 chunk 的重试资格。不能自动跳过、换新 session 或删除原始数据。需确定可重试原因、次数、退避、资源预算与终止条件。
6. **实际存储计划。** 当前最多保留八个路由代际，磁盘也是有限的。归档、空间预留和原始证据生命周期必须与旧 attempt 回读、Android 确认和结果完整性相容。没有自动删除未确认数据的授权或实现。
7. **可操作状态。** 需要一个统一入口说明活动 span、待处理输入、剩余容量、已导出的结果，以及当前暂停的准确原因和恢复命令；不能把局部“健康”返回当成整条流水线正常。

## 本轮身份组延续能解决什么

显式保留既有审核身份组，让新会话继续访问同一组已存在的审核资料。它不新增人物、不自动登记声音、不复制局部 speaker 标签，也不把组成员关系变成识别准确性的证明。原始 PCM、帧范围和转写内容不因这一配置而改写。

现有 primary voice references 只产生片段级人物建议，不替代全文说话人标签。只有人工人物关联、没有另行登记声音参考时，保持身份组后仍可能没有任何声音建议。研究标签不能代替登记 API 要求的人工听审确认。

## 仍未解决的识别问题

- 实际严格模式使用 SenseVoice；没有文本 prompt 或可跨会话序列化的解码器状态入口。
- 原来的同会话 native 上下文不等于跨会话上下文。把前一会话音频当作新会话上下文，需要另外定义来源、所有权及边界去重，不能直接拼进去。
- 先前对照中增加两秒声学上下文使总词错误从 97/329 增至 108/329；固定英语也没有总错误改善。本轮不重复这些参数扫描。
- 跨边界文本上下文、跨人声身份、重叠发声、小音量人声和长时稳定性仍需独立真实语音证据。短公开片段上的匹配结果不能替代部署到其他服务器、实际手机或长时运行验收。

现阶段操作应保持显式、逐步、可恢复。不要把上述缺口隐藏在更大的测试计数或更高的容量配置后面。
