# Verified source retirement contract

Design-only source-retirement contract that complements `PRIMARY_HISTORY_AUTHORITY_DESIGN.md`. It supersedes the earlier proposal to reopen every original upload after every restart: already verified-retired source versions need no live file to retain admitted identity evidence. No retention action, migration or production implementation is authorized here.

Source baseline: `Headmaster218/long-audio-backend` commit `b13c6fc4f1e5f3d9f86b68a222d4cab3c78101de` (operational baseline `49cd724dda5595aee29eaf1d7da2f41739b43d08`). Comparator evidence is retained under `prototypes/history_comparator/`; it does not qualify production resource use or identity accuracy.

## Minimal distinction

Use one source-version authority row per distinct bound source version, scoped to its recording. Its durable state is exactly `active`, `retired` or `revoked`. Explicit session erasure deletes the row and derived data. Source version binds the exact admitted Receipt bytes, owned-path digest and recording/source mapping digest; it is not an owner-process epoch. The original upload path remains in retained chunk metadata, so the marker need not duplicate a 4 KiB path.

- `active`: fresh admissions require the existing exact live authority checks. After restart, positive active-source authority requires bounded proof/mapping/owned-file signature revalidation; unmarked missing files remain unknown.
- `retired`: an acknowledged immutable retirement marker preserves the authority of the marker's exact already-admitted certificates. It forbids all new capture, reservation, inference and certificate append using that source version. Retired observations, aliases, cannot-links and other competitors remain fully present in comparisons. This is not permission to turn old audit-only packets into certificates.
- `revoked`: explicit source revision, tampering, bound mapping mutation, cancellation or destructive recording action fences the scope under the existing destructive-invalidation contract. Retained evidence remains auditable, never silently removed from competition to improve a merge.

`retired` means evidence retirement was verified and new admission closed; it does not mean the file was physically deleted. A separate cleanup field has exactly `pending`, `done`, `failed` or `unknown`. Historical read wording is “validated at admission; source version verified retired,” never “current file verified.” Ordinary receipt/core/crop GC still does not change this source state.

## Small typed state and marker

The source-version row contains recording/source keys, source-version digest, state, a nonnegative signed 63-bit source-specific admission revision, admitted-certificate count and maximum required committed end frame. It increments admission revision/count only when a new successful certificate binds that source. Unrelated new uploads or certificates do not change these counters. Forward primary progress is harmless; moving progress behind an already certified required end is destructive.

One immutable retirement marker per source version contains: schema 1; fresh 16-byte operation token; source-version/Receipt/owned-path/mapping digests (32-byte SHA256 values); source-specific admission revision and count; digest of the exact sorted admitted-certificate/basis/proof-reference set; completed validation evidence digest; current durable recording authority revision; and a retirement policy ID. Its canonical body is at most 1,024 bytes. Set digest includes certificate IDs, their vector/crop/proof digests and typed origin IDs; no vectors, labels, audio or proof bodies are copied into the marker. The existing immutable objects remain retained and charged. Missing required proof, inconsistent counts or an empty/unknown certificate set refuses this identity-retirement operation; unobserved source cleanup is a separate existing retention concern.

Charge 512 bytes per source-version row (bounded numeric/reference payload <=256 bytes), and len(marker body)+512 bytes per retirement marker, maximum 1,536. Cleanup state/reason/counter fields fit the marker's fixed 512-byte allowance: one enum, a saturating nonnegative 31-bit attempt counter, nullable reason from `io_unavailable`, `path_changed`, `storage_unknown`, `other`, and no free-form exception/path log. A primary source used once therefore adds at most 2,048 bytes across source authority and retirement, about 5.63 MiB for 2,884 distinct sources. Shared source versions are charged once. These bytes join the same proposed history quotas; marker saturation refuses retirement and leaves the source active, rather than deleting proof or audio.

## Ordering and ownership

There is no new retention service. A caller with separately approved normal-retention authority invokes a narrow helper in the proposed history module before deleting an original. Existing cleanup ownership and bounded maintenance turns perform the later unlink. This contract does not choose retention ages, authorize deletion of additional files, or assert that routine original-upload retirement is already implemented. `lifecycle.unlink_owned` is the existing ownership-bound unlink primitive; its session-erasure caller is not automatically a safe identity-retirement dispatcher.

1. Select a completed immutable source version that the existing retention policy permits to retire. Require no primary processing, waiting/provisional crop, admitted optional operation or unknown invocation still using it. Current generation/operation closure must be positively known. If busy or unknown, defer; no lease is held while waiting.
2. Read the exact retained certificate/proof/dependency set using bounded indexed pages, compute its digest, and validate all retained bytes. Revalidate the live owned-file signature and exact source/mapping facts under the existing owned-file contract. Signature continuity checks device/inode/size/mtime_ns/ctime_ns, not a new whole-file content hash. Paginated preparation is provisional and grants no deletion permission.
3. Under the existing publication/admission guard, perform one bounded primary-DB transaction. CAS the source's exact version, `active` state, source-specific admission revision/count, required end, current mapping and recording authority revision. Recheck quiescence and validation evidence. Insert the immutable marker, change source state to `retired`, set cleanup `pending`, and charge accounting atomically. New admission checks that same source state at reserve, dispatch and append, so an earlier candidate cannot race across retirement. Failure rolls back. All aliases referring to the same owned path/version must be covered or retirement is refused; do not unlink a file still owned by an active source alias.
4. Only a positively acknowledged exact marker authorizes its corresponding cleanup attempt. A failed or unknown marker acknowledgement means no unlink by that caller. Exact storage resolution is closure-only; a later bounded cleanup pass may act after it independently and positively reads that exact committed marker and verifies its token/version. It may not infer marker existence from a missing file.
5. Before unlink, resolve the path from retained metadata and require its digest and current file signature to match the marker's source version. If the original is already absent and the exact marker exists, cleanup can be reconciled as done. If the path now refers to changed/replacement bytes, do not unlink it; apply destructive invalidation or mark authority unknown if that write cannot complete. Use the existing owned-directory/no-competing-writer contract and guard; do not claim an atomic inode-conditional unlink against arbitrary external filesystem attackers.
6. Perform the owned unlink, then record cleanup result under the exact marker token. An unlink failure leaves harmless retained bytes with `failed`/`pending` cleanup; the verified-retired certificates remain usable. Unknown unlink outcome remains `unknown`; exact path/token reconciliation distinguishes present-same, absent, and changed. Never claim physical cleanup until positively known. Cleanup retry cannot reopen source admission.

The source marker is the authority transition, not the filesystem side effect. A crash before marker commit leaves an active source and no cleanup permission. A crash after marker commit but before unlink leaves extra bytes; after unlink but before cleanup acknowledgement, the marker proves the absence was authorized and permits idempotent cleanup reconciliation. Neither case requires loading audio to read retired evidence. An unmarked disappearance cannot be repaired by retrospectively issuing a marker from hashes alone.

## Destruction, reads and tests

A final decision publication checks each source's current durable state/version and either its active-source validation or matching retirement marker. A valid active-to-retired transition does not alter embeddings, history membership, source aliases or hard witnesses, so exact score-cache prefixes remain reusable. It cannot strengthen a decision by dropping a competitor. The full-history final revision CAS and proof-availability checks still apply. A retired marker never authorizes a fresh embedding, even if the file happens to remain present.

Explicit cancellation/tampering/revision still performs the destructive scope fence atomically. Explicit session erasure must delete certificates, vectors, aliases, witnesses, proof objects, retirement markers and decisions, update usage, and retain only existing scrubbed erasure/cleanup intent as permitted by lifecycle policy. It must not merely set `retired`. Deleting shared objects without all references erased is forbidden.

Required synthetic cases: ordinary append outside bound source remains stable; retirement closes racing capture/reserve/append; pending/unknown invocation blocks retirement; marker commit failure and lost acknowledgement cause no unlink; exact later committed-marker recovery; crash before/after unlink; unlink failure leaves usable retired evidence; replacement path is never deleted; unmarked missing source remains pending across restart; retired observations/aliases/hard competitors still affect margins; no audit-only packet promotion; source tamper/cancel fences; erasure actually removes derived identity data and adjusts all refcounts/charges. No tests or cleanup actions have run for this addendum.
