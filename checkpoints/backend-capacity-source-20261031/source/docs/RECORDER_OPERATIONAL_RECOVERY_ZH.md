# 异步处理与中断后的显式恢复

EOS 提交成功不等于模型已经完成。`run --finalize --export` 可能正常返回 pending。
需要等待时使用同一个 runner 的有界 `watch --finalize --export`，不要因为 pending
新建 session、复制原录音到替代任务，或立即停止正在处理的服务。

## 严格任务被中断

严格模式在无法证明子进程清理完成时保留现场并停止推进。重启后，未解决的运行任务
可能被标为 failed/manual，错误为 `Strict processing interrupted; manual retry required`。
这是需要明确处理的状态，不是自动恢复成功，也不表示原录音已经丢失。

1. 保留原数据目录、instance.lock、runner/job、原录音和所有已有结果。
2. 用原配置启动同一服务；检查健康状态和原 chunk 的当前状态、错误、session 归属。
3. 只有确认是这个失败的严格任务并决定重试时，调用原服务的
   `POST /chunks/<确切的原 chunk ID>/retry`，无请求正文。
4. 不使用 `/resume`，严格任务明确拒绝它。响应不确定时先 GET 原 chunk 检查现状，
   不盲目再次 POST，不创建替代 session。
5. 保持服务运行，观察原 chunk 完成或出现新的明确阻塞；随后对原 runner 继续
   watch/status/export。只有保存并核验导出结果后才把这段分析视为完成。

重试接口保留原音频、工作回执和已保存的进度/结果，重新授权同一严格任务处理。
当前没有自动调用该接口的无人值守重试策略。

## 已实际验证的有限场景

2026-11-04 云端公开语音夹具中，一份3秒、48000帧的逻辑分析尾段在转码期间被停止。
重启后保持 failed/manual；随后只对原 chunk 调用一次 retry，原生处理完成并保存
一段转写。原 WAV 和交付摘要、原 session、EOS 和0–48000帧范围均未变，没有新会话、
没有数据库手工修改。服务最终正常退出，锁释放且无遗留子进程。

该场景初次中断时尚未保存转写（cursor=0）。它不证明任意已产出部分转写的中途崩溃、
断电、磁盘故障、无限次数重试或所有目标服务器都可恢复。识别质量仍需另行验收。
