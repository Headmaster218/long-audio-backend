# dev67 完整安装后三代际实际流程

## 这次验证了什么

在同一台云主机的全新 Python 3.13.5 环境中，安装完整 dev67 wheel 和32个固定hash
依赖。所有 Python 客户端、FTPS接收器和原生分析服务都以 `-I -B` 使用已安装包，
没有把源码或测试工具加入产品运行路径。Java端使用未改动的 Android 生产FTPS传输/
网络类及主机适配夹具，不是实体手机测试。

固定账号、端口和远端基础目录依次服务A/B/C三个接收代际。三份真实公开语音原始
录音各3秒，producer close_reason分别为ROTATION、ROTATION、STOP：

1. A接收第一份，初始化并完整接收旧分析段。
2. 完成上传后明确停止/重启接收器，B接收第二份，同时仍能只读回A的原attempt。
3. 有界交接命令固定路由文件、准确继任者、两侧发布区和下一session计划，保存逻辑
   边界，终结/导出A的分析段，然后只创建一次准确的B分析session。
4. 同样切到C。A/B旧attempt仍能读回；第二次跨inbox交接完成后，C分析真实STOP段。

切换接收器是受控停止/重启，发生在上传已经完成之后。没有验证上传途中无损热切换，
也没有让配置文件冒充实际运行状态。交接入口本身不控制接收进程、不自动开始下一段
摄入、不安装后台守护程序。

## 字节、帧及结果

- 三个session恰好各有一个完成的原生分析chunk，各48000帧。
- 解码三个原生分析WAV并按原序号拼接，逐字节等于原144000帧单声道16k PCM。
- 原范围连续为0–48000、48000–96000、96000–144000；无补零、截断、遗漏或重复帧。
- 每代只有一份原attempt；raw/published三对象摘要匹配Java回执，解包后的producer
  元数据逐字节等于原manifest。原WAV、原spool及A/B已有文件摘要保持不变。
- 两份逻辑导出明确标记recording_complete=false、recognition_continuity_verified=false，
  不篡改ROTATION。三份导出的complete.json提交摘要均可重新核验。
- 三段分别观察到1、1、4条非空主转写。它们不是准确率分数，也不证明分段后的文字、
  语义上下文或说话人身份与单一连续session相同。
- 完成后重复两个交接命令均为0 HTTP请求/写入，没有额外session。

## 实际异常与恢复

第一次有界交接在提交EOS后因轮询上限暂停，下一session尚未创建。随后故意停止
正在执行的原生服务，再启动同一数据目录，原chunk保留为failed/manual，错误为
`InterruptedError: Native diarization interrupted`，cursor=0，48000帧原音频及工作回执保留。

夹具最初只接受另一个中断错误文本，因而停止了验证。只读确认实际failed/manual
状态及重试条件后，在同一session、同一chunk调用了一次明确的retry，再从原交接
回执继续。没有替代session、数据库手改或删除原数据。最终三个原任务都完成。
重试资格取决于真实状态，不应该只匹配错误字符串。

三个接收进程均正常退出0；原生进程各次等待结果为143，最终无遗留子进程。
采样原生RSS峰值799207424字节，仅为本次观察，不是硬资源上限证明。
